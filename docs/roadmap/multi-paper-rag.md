# PaperBase 多论文检索、比较与归纳 Roadmap

> 状态：`PLANNED`
> 当前正式 Evaluation 仍限定为单论文、Context-free Retrieval Benchmark。

## 实施状态

| Phase | 状态 | 说明 |
|---|---|---|
| Phase 0：多论文验收集 | `NOT STARTED` | 当前 Golden v1.2 只评单论文。 |
| Phase 0.5：首页元数据与标题 | `COMPLETED` | 已有结构一致性标题解析和回归测试。 |
| Phase 1：论文实体与别名 | `PLANNED` | 尚无完整论文别名索引。 |
| Phase 2：结构化 Query Planner | `PARTIAL` | 已完成 Resolution/Rewrite 可靠性修复，但未实现多论文计划契约。 |
| Phase 3–7 | `PLANNED` | 尚未进入实现。 |

## 1. 定位与边界

当前 v0.1 已完成论文知识库的主链路：PDF 解析、语义切块、SQLite/FTS5、向量化、FAISS、混合检索、Query Rewrite、参考文献辅助检索、Reranker、邻居扩展和带引用回答。

v0.1 的优势是单论文事实、方法和细节问题能够稳定地完成“检索证据后回答”。本 v1.1 优化计划的目标不是替换这些能力，而是在其上新增**多论文问题编排层**，让系统能够可靠处理论文比较、论文发现和全库归纳。

本计划只记录 v1.1 的后续优化方向，不代表当前已实现，也不改变 v0.1 的运行行为。

## 2. 要解决的问题

跨论文比较不能只依赖全库一次 Top-K 检索。例如用户问“论文 A 和论文 B 有什么区别”时，若论文 A 的 chunk 得分普遍更高，论文 B 可能在 Dense、BM25、RRF 或 Reranker 阶段之前就被淘汰。此时回答模型即使能够比较，也没有论文 B 的证据可用。

v1.1 的核心目标是把检索目标从：

```text
找到全库最相关的若干 chunk
```

升级为：

```text
在保持相关性的前提下，为问题要求涉及的每篇论文保留充分、可引用的证据。
```

## 3. 问题类型

| 类型 | 示例 | 检索目标 |
| --- | --- | --- |
| 单论文事实/细节 | “本文用了什么数据集？” | 找到指定论文的局部证据。 |
| 单论文整体总结 | “D2STGNN 的整体方法是什么？” | 找到该论文多个章节的代表性证据。 |
| 指定论文比较 | “A 和 B 的预测目标有什么区别？” | A、B 每篇论文均需有证据。 |
| 论文发现/列表 | “哪些论文使用了 GNN？” | 在全库发现多篇满足条件的论文。 |
| 全库统计/归纳 | “当前库中有多少篇使用 GNN？” | 尽可能覆盖当前全部已入库论文。 |
| 无答案/歧义 | “那个模型怎么样？” | 通过上下文定位；无法定位时说明或追问。 |

`search_bibliography` 保持为独立开关，而不是主问题类型：它表示是否要额外查询参考文献。正文检索始终保留。

## 4. 目标架构

```text
用户问题 + 有限对话上下文
        ↓
规则优先的查询理解
        ↓
论文实体解析（标题、别名、作者-年份、本文/它）
        ↓
LLM Query Planner 处理规则无法确定的部分
        ↓
结构化检索计划
        ├── 单论文：限定论文范围的 Hybrid Retrieval
        ├── 指定比较：每个目标论文分别 Hybrid Retrieval
        ├── 论文发现：全库检索后按论文聚合
        └── 全库归纳：逐论文覆盖与统计
        ↓
RRF / Reranker / Section-aware Neighbor Expansion
        ↓
论文覆盖校验与缺失论文的定向补检索
        ↓
按问题类型组织证据并生成带引用回答
```

## 5. 分阶段实施计划

### Phase 0：建立多论文验收集与基线

在改变检索逻辑前，先固定一组中文问题和人工确认答案，至少包括：

- 两篇指定论文的方法、数据集、预测目标比较；
- “哪些论文使用某方法”的列表问题；
- 全库统计问题；
- 指代型问题，例如“本文”和“那个模型”；
- 需要正文与参考文献共同支持的问题。

新增指标：

- `paper_resolution_accuracy`：论文标题/别名是否被正确定位；
- `evidence_coverage_at_k`：被指定的每篇论文是否进入证据集合；
- `comparison_coverage`：比较问题中各论文是否都有有效证据；
- `citation_precision`：引用是否支持对应结论；
- `no_answer_safety`：没有证据时是否拒绝编造。

### Phase 0.5：首页元数据与标题锚点鲁棒性

在多论文实体解析依赖 `documents.paper_title` 之前，先补强 Docling 首页的通用标题与前置元数据识别。该阶段不针对某个已导出的 Markdown 打补丁；修复必须发生在 `ParsedPaper` 的通用结构化解析层，并由重新解析生成 Markdown、chunks 与元数据。

已发现的真实边界案例：Elsevier/ScienceDirect 首页同时有期刊名和论文题目时，`Energy` 因较短而被现有标题回退规则排除，但 `Expert Systems With Applications` 因长度较长被误选为论文标题。后者又会使“标题到下一个强边界”的作者单位扫描在真实论文题目前提前结束，导致 `Front matter > Authors and affiliations` 缺失。

优化目标：

- 改进首页标题候选排序，排除期刊名、`journal homepage`、`Contents lists available` 等出版栏元素，而不只依赖最小文本长度；
- 保持真实论文标题、作者、单位、通讯作者、关键词和摘要之间的文档树顺序与页码 provenance；
- 让无显式标题的作者单位块仍能以真实论文标题为左边界插入 `Authors and affiliations`；
- 不以文件名、论文题名白名单或直接编辑 Markdown 的方式修复单篇论文；
- 将 Saeed（期刊名 `Energy`）和 Qiu（期刊名 `Expert Systems With Applications`）的首页作为成对回归样本，验证两篇都得到正确的 `paper_title` 和 authors/affiliations 前置块。

新增验收指标：

- `paper_title_accuracy`：论文标题不得被期刊名、栏目名或摘要标题替代；
- `front_matter_authorship_recall`：具备作者与单位信号的首页应生成作者单位块；
- `front_matter_provenance_integrity`：标题、作者单位与后续正文的页码和阅读顺序不被修复过程破坏。

### Phase 1：论文实体解析与别名

扩展 `documents` 的论文可识别信息，建立标题别名能力：

- 规范论文标题；
- 大小写、标点和空白归一化后的标题；
- 文件名；
- `第一作者-年份` 表达；
- 已确认的短标题、模型名称和常用缩写。

处理顺序应为：精确规则匹配优先；规则结果不唯一或不存在时，才让 LLM 在候选论文中辅助选择；LLM 不得凭空创造论文实体。

### Phase 2：结构化 Query Planner

在现有 Query Rewrite 的基础上新增“检索计划”输出或独立规划步骤。计划至少包含：

```text
intent                    # 问题主类型
target_paper_ids          # 已解析出的目标论文，可为空
comparison_dimensions     # 可选，例如方法、数据集、输出形式
search_bibliography       # 是否额外检索参考文献
requires_complete_set     # 是否请求“全部/多少篇”等完整性结论
```

其中明确的标题、引用编号和参考文献表达应由程序规则优先处理；LLM 只处理语义歧义与比较维度理解。

### Phase 3：按论文范围执行检索

本阶段是 v1.1 的核心。

对于指定论文比较，执行：

```text
Paper A：Dense + BM25 → RRF → Reranker
Paper B：Dense + BM25 → RRF → Reranker
```

两条路径彼此独立，不能让论文 A 的高分 chunk 挤掉论文 B 的候选。每篇目标论文应保留可配置数量的高质量证据。

实现原则：

- SQLite FTS5 可以通过 `paper_id` 直接限定 BM25 范围；
- 当前全局 FAISS 不原生理解 `paper_id` 元数据；v1.1 初期可按 `paper_id` 找到合法 `vector_id` 后，仅在该集合内计算 Dense 相似度；
- 当前库规模较小时不建立轻量子索引；未来 chunk 量增长后，优先评估迁移到支持 metadata filter 的向量数据库，而不是预先维护多个子索引；
- 禁止仅通过“全局 Top-K 后过滤 paper_id”来保证比较覆盖，因为它不能保证弱势论文进入候选集。

### Phase 4：发现型问题的论文级聚合

对于“哪些论文使用了某方法”类问题，目标论文在检索前未知，因此仍先运行全库 Hybrid Retrieval。

检索后按 `paper_id` 聚合：

- 每篇论文选取 1 至 2 个最能证明条件成立的 evidence chunk；
- 控制单篇论文的最大输出数量，避免它占满列表；
- 输出以“论文”为单位，而不是以 chunk 为单位；
- 回答措辞使用“当前已入库论文中检索到”，除非已完成全库覆盖验证。

### Phase 5：全库统计与归纳

“多少篇”“全部有哪些”是覆盖问题，不能将检索 Top-K 当作全集。

- 能由结构化字段回答的问题，优先 SQLite 聚合；
- 需要理解正文才能判定的条件，应按论文逐篇评估或建立文档级索引；
- 若没有完整覆盖能力，回答必须说明它是“检索到的结果”，不能声称“全部”。

后续可选优化：为每篇论文的标题、摘要、关键词和受控摘要建立文档级向量，以支持“先选论文，再检索 chunk”的两层检索。

### Phase 6：覆盖校验与定向补检索

在最终回答前执行确定性校验：

```text
expected_paper_ids 是否全部出现在最终 evidence 中？
```

若比较题缺少某篇论文：

1. 仅针对缺失论文再次定向检索；
2. 再次进行 Reranker 与邻居扩展；
3. 仍无证据时，回答明确说明该论文在该维度上证据不足。

不得让回答模型自行补写缺失论文的结论。

### Phase 7：比较型回答与引用约束

为比较题单独准备回答提示词与证据组织方式：

```text
比较维度
论文 A 的证据与结论
论文 B 的证据与结论
共同点 / 差异
无法可靠比较的维度
```

每项论断必须能对应到所属论文和 chunk 引用。参考文献仅用于识别被引工作或补充书目信息；“作者为什么引用某工作”仍必须以正文中的引用语境为主要证据。

## 6. 非目标与设计约束

- v1.1 不替换 v0.1 的解析、切块、embedding、FAISS、Reranker 或回答链路；
- v1.1 不在当前小规模库中提前建立每篇论文的轻量 FAISS 子索引；
- 不因检索结果有限而宣称“所有论文”；
- 不让 LLM 猜测不存在的论文、缩写含义或比较结论；
- 单论文检索应继续保持当前的性能与行为，新的多论文策略仅在对应意图下启用。

## 7. 完成标准

v1.1 完成时，至少应通过以下验收：

1. 指定两篇论文比较时，最终证据中两篇论文均有来源；
2. “哪些论文……”的输出按论文聚合，且不会被一篇论文的多个 chunk 垄断；
3. “全部/多少篇”问题不会把 Top-K 误称为全集；
4. 无法解析论文实体或证据不足时，系统安全说明限制；
5. v0.1 已通过的单论文问答、参考文献检索与无答案保护不回归。
